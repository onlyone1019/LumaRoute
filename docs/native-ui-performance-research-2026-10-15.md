# 原生 Mac 应用交互性能调研与 LumaRoute 优化顺序

调研日期：2026-10-15。基线：`f582cee` / 已安装 Release Build 27。本次仅采样、隔离测量和查阅一手资料，没有修改应用代码、配置、节点选择或重启在线服务。

## 结论

原生客户端的响应速度依赖于交互路径上的工作量、数据依赖范围和状态生命周期。LumaRoute 目前已有原生控件、流量状态分离、SQLite 异步写入以及规则专用保存路径，但这些不能替代界面响应验收。

下一轮应集中处理菜单增量更新、后台状态去重、页面刷新解耦和编辑器候选缓存，先保留现有 SwiftUI / AppKit 组合，再依据测量决定局部是否需要使用 AppKit 容器。不能从使用原生语言或业务保存较快直接推导出 UI 足够流畅。

## 当前测量及其边界

通过 CUA 在已安装应用中依次切换概览、订阅、代理、规则、日志、设置等页面，同时运行 `sample` 采样。未在这一轮捕获到明确的半秒级持续主线程阻塞；辅助功能树读取本身在采样中有显著开销，不能把自动化调用耗时或其产生的调用栈直接当作用户点击耗时。

另构建隔离的原生测试宿主，使用当前源码、Release 优化、相同的 14 个策略组和当前 `/proxies` 只读快照，调用实际 RootView 与 StatusMenuController。测试宿主不 bootstrap、禁止刷新、不启动内核，SQLite 只读；窗口未显示。测量页面赋值后的同步布局 / display 调用，以及真实菜单构建方法。

| 测量对象 | 结果 |
| --- | --- |
| 菜单每次完整构建，10 轮 | 60.4–76.0 ms，中位数 65.4 ms |
| 概览同步布局，3 轮 | 36.9–52.2 ms |
| 订阅同步布局，3 轮 | 56.2–95.6 ms |
| 代理同步布局，3 轮 | 92.9–114.0 ms |
| 规则同步布局，3 轮 | 48.1–62.0 ms |
| 日志同步布局，3 轮 | 43.8–55.1 ms |
| 设置同步布局，3 轮 | 78.0–98.5 ms |
| 两个后台状态属性各赋相同值 10 次 | 20 次赋值，20 次 `objectWillChange` 通知 |

这些是隔离组件成本，不是点击到屏幕呈现的端到端延迟，也不能彼此相加。通知次数不等于实际绘制次数，SwiftUI 可能合并更新。它们说明存在重复工作和较高的前台组件成本，尚不能证明每个操作都由同一个原因拖慢。

私有脚本、JSON 和采样位于 Git 忽略的 `work/ui-responsiveness-2026-10-15/`，不上传当前用户数据。当前 CLT 环境无 `xctrace`，本轮未执行完整 Instruments SwiftUI / Hitches 录制。

## 官方指导与源码对照

### 1. 以输入响应和帧预算验收

Apple 将离散交互约 100 ms 作为可感知延迟参考，建议主线程可用预算按不到其中一半考虑；连续交互通常需要把相关工作控制在约 5 ms。业务完成用时与点击反馈应分别测量。[Improving app responsiveness](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)

WWDC26 推荐先判断 CPU 忙碌、执行争用还是系统等待，再选择优化算法、转移计算或分析 I/O / IPC；使用 Release、signpost 与前后对照验证。[WWDC26](https://developer.apple.com/videos/play/wwdc2026/268/)

### 2. 只让有关的数据触发有关的视图更新

Apple 明确指出，频繁的小更新也会产生性能问题；昂贵计算应异步处理并缓存。Observation 能按实际读取的属性建立依赖，减少整对象观察造成的无关更新。[SwiftUI 性能指导](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance)、[模型依赖追踪](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app)

LumaRoute 的 `RuntimeData` 已采用 `@Observable`，但 `AppStore` 仍是广泛共享的 `ObservableObject`。`refresh` 中的 `serviceRunning`、`canRollbackGeo` 每轮直接赋值，即使相同也发布通知。先做等值去重和拆分依赖，再判断是否迁移其余状态；不把全面改宏当成自动解决方案。

### 3. 菜单和弹窗复用，只有结构变化才重建

LumaRoute 的 `menuNeedsUpdate` 每次先 `removeAllItems`，随后创建所有组的子菜单、节点、文本列和测速视图。可把静态命令保留，按组 / 节点结构签名决定是否重建；勾选、标题、延迟和启用状态单独更新。较大的组可在实际展开时生成，展开期间不破坏菜单结构。原生菜单项仍由主线程更新，预先计算可独立执行的展示数据。

Stats 对已有弹窗的复用、隐藏时缓存数据并在显示时回放，以及 sing-box Apple 的快照与分组去重，提供了实际源码参照；具体版本、行号和限制见[源码调研](native-app-source-practices-2026-10-15.md)。这些实现并不证明其每次操作一定更快，也不意味着应让 LumaRoute 所有页面永久驻留。

### 4. 页面先显示可用快照，再按需补新数据

LumaRoute 的 `page.didSet → requestRefresh → refresh(force:true)` 会让页面切换强制进入节点和 provider 刷新判断，即使目的页是设置或订阅。网络等待本身是异步的，不能直接称为主线程阻塞；但额外请求、解码和状态提交会增加切换后的竞争与更新。

页面切换应与用户明确点击“刷新”区分。按当前页面、数据时效和配置版本安排请求；先显示缓存，后台补新数据并丢弃过期结果。保留搜索、展开、选择和草稿等页面状态，依据测量决定是否保留昂贵的宿主视图。

RootView 用条件分支切换页面；分支状态生命周期随结构身份变化。Apple 提醒身份变化会重置状态，因此应明确选择哪些状态需要跨页面保留，不能随意用变化的 `.id` 触发重建。[StateObject 与身份](https://developer.apple.com/documentation/swiftui/stateobject)

### 5. 异步提交配合即时、可信的反馈

sing-box Apple 的节点选择可作为 pending 状态反馈的参照，具体代码见源码调研。对 LumaRoute，菜单打开、页面切换和弹窗出现不应等待配置解析；业务操作显示“处理中”，成功才确认、失败则保留原选择并给出错误。

编辑器虽然使用 `.task`，其中仍同步调用 `compositionPolicyTargets`，需要读取缓存并组合、解析 YAML。`.task` 不代表计算自动移到后台；Apple 对此有明确的主执行器继承说明。[后台执行教程](https://developer.apple.com/tutorials/instruments/ensuring-work-executes-in-a-background-thread)

可按订阅缓存版本、成员、基础配置和实际影响候选的参数缓存展示模型。后台对不可变输入生成候选，主线程仅提交结果；输入变化、取消和旧结果覆盖需要一并处理。加载中继续保留已选出口，加载失败与真实缺失分开显示，延续 Build 27 的误报修复。

## 建议实施顺序与验收

| 优先级 | 改动 | 验收重点 |
| --- | --- | --- |
| P0 | 相同后台状态不发布；收窄 UI 观察依赖 | 稳态心跳不产生无关更新；测速 / 流量变化仍正常显示 |
| P0 | 菜单结构复用，动态字段增量更新 | 同一配置再次打开不重建全树；展开时更新不抖动、不丢选择 |
| P1 | 切页与强制刷新解耦，页面状态保留 | 设置 / 订阅页切换不强拉 provider；返回页面保留必要状态 |
| P1 | 编辑器候选模型缓存与后台生成 | 首次打开立即有可用界面；旧请求不能覆盖新组合，失效校验仍准确 |
| P2 | 根据数据局部调整宿主 / 列表结构 | 仅在 P0/P1 后仍存在布局热点时考虑 AppKit 容器或表格 |

下一轮的项目目标：简单交互首个可见反馈 P95 小于 50 ms；复杂页面首个可用界面 P95 小于 100 ms；相同菜单重复打开不再进行全量重建。它们是待测的项目目标，不是已经达到的结果或对所有硬件的保证。需要建立输入事件、状态切换、布局和最终呈现的测量边界；窗口隐藏状态下的布局数字不能替代最终实机端到端验收。

覆盖首次与重复打开、正常和较大订阅、测速 / 流量刷新同时发生、快速切页及取消操作。规则保存和网络切换继续单独验收，确保本轮 UI 优化不改变既有配置、连接或规则语义。
