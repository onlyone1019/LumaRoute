# Build 27：分流规则保存性能

## 改动

- `CoreRunner.validate` 使用独立、随机的校验目录。GeoData 从原运行目录只读链接，受管 provider 路径限定在原运行目录；校验结束或取消后清理目录和日志。校验进程不再争用在线内核的 `cache.db`。
- 新增 `apply-routing` 后台请求。前台保留输入校验，后台统一生成完整候选并执行最终安全检查和内核校验，避免前后台重复生成、校验。
- 后台检查已应用网络参数、调用方控制凭据、当前内核版本和网络所有权；纯规则更新不会提交系统代理或 DNS 设置。
- `RoutingUpdatePolicy` 比较新旧配置拓扑，仅允许规则和独立处理的模式字段变化；受管 revision 路径可变化，URI / 本地规则缓存内容仍需一致。节点、DNS、端口、TUN、策略组、provider URL 或缓存内容变化须走完整配置更新。
- 相同监听端口的规则更新使用 `force=false`，保留内核进程和已有连接；模式以实际运行值核对，失败回滚保留实际模式。
- 分组只恢复发生变化的选择。自动组的当前节点与手动固定状态分别判断，避免把“恰好选中”误认为“已经固定”。
- 活跃组合仅修改分流或自定义规则时走专用路径；成员、基础订阅、兜底等结构变化沿用完整流程。规则保存保留流量 / 日志观察任务、节点测速结果和 provider 元数据。
- 内核候选失败不触发重复全量应用；SQLite 写入失败通过规则路径恢复原有内核规则及业务数据。

## 测速

使用当前用户配置的私有副本（26 个节点、14 个策略组、约 1100 条基础规则），独立端口 19984 / 19985。旧版二进制在修改前保留，前后均使用已预热 GeoData、相同规则新增场景；数据只写入私有测试 SQLite。

| 流程 | 保存核心流程中位数 |
| --- | ---: |
| 优化前，3 轮 | 1551.8 ms |
| 优化后，5 轮 | 182.4 ms |
| 减少 | 88.2% |

上述时间包含组合生成、后台候选安全检查 / 生成 / 校验 / 应用、选择恢复以及 SQLite 提交。旧版还包括其重复的前台生成 / 校验。未计入真实 XPC 往返、窗口渲染及旧版系统网络提交，属于隔离核心流程测量，不等同于在线界面点击全程耗时。

另以真实 AppStore、两个本地模拟出口和独立 SQLite 测量完整的 `saveComposition` 方法，保存约 78 ms（小型 fixture）。普通自定义规则也验证走同一路径。
