# 0.1.18 性能检查

基线：`71b643ad90f76bbe6dd62ae4c7a6ef4551979ae8`，0.1.18 / Build 48。环境：Apple M1 Max、macOS 27.2.1、SDK 27.2、Swift Release 优化构建。

结论：发现四项可进一步减少界面工作的机会，最值得先处理连接页重复筛选排序。没有证据支持调整代理转发内核、降低健康检查频率或删除配置验证。本次为检查及隔离原型对照，未修改产品源码，未操作已安装应用、用户数据库、管理员服务、系统代理或 TUN。

## 方法与边界

- 从当前源码构建到本次独立 work 目录，不覆盖 dist 或已安装应用。
- 连接页、日志页、菜单使用生产视图、AppStore 和核心模型；测试宿主不执行 bootstrap，设置 shuttingDown，仅注入合成数据。未发送真实 XPC 请求。
- 连接页在源码副本的 items getter 中计数、累计执行时间，在表格 reloadData 调用处计数。每种场景执行 6 次；比较现有实现和“同一轮 body 计算一次，再把结果传给计数、表格、选中详情和空状态”的副本。
- 全部编译结束后串行运行两轮现有实现、对照副本和日志/菜单测试。下表为两轮结果范围，每次事件的计算耗时为该轮 6 次累计耗时除以 6。
- 页面检查确认列表初始行数与搜索后的行数正确；这不是所有功能的回归验收，隔离原型不能直接视为可发布补丁。
- 这里的 getter 时间不含布局、绘制、网络、刷新等待或物理输入到屏幕出帧时间。10,000 条连接和 20,000 个菜单条目是扩展规模压力样本，不代表用户当前负载。
- 进程补全调用真实只读系统进程查询，连接为合成数据；索引原型只用于确认查找成本，比较输出的进程路径及来源一致。

## 1. 优先：连接页一次渲染重复计算四次

位置：`Sources/LumaRoute/Views/ConnectionsPage.swift:18`。标题计数、表格数据、选中项查找、空状态分别读取 items。即便只是改变 selection，同一批连接仍完整筛选排序四次。

真实页面两轮计数都为每次事件 4 次；单轮共享结果的隔离副本为 1 次。

| 合成连接数 / 操作 | 现有实现计算耗时 | 单轮共享结果副本 |
| --- | ---: | ---: |
| 300 / 输入搜索 | 8.68–8.70 ms | 2.22–2.25 ms |
| 2,000 / 输入搜索 | 57.85–58.81 ms | 14.77–14.81 ms |
| 10,000 / 输入搜索 | 292.13–294.86 ms | 73.83–74.15 ms |
| 2,000 / 仅改变选择 | 28.47–28.64 ms | 7.14–7.23 ms |
| 10,000 / 仅改变选择 | 185.14–189.36 ms | 47.53–47.77 ms |

这部分主线程计算可减少约 75%。这不是整页刷新或整体 CPU 降低 75%；万条连接单次计算仍可能占用几十毫秒。

建议先采用每轮渲染共享结果，不引入跨轮缓存、不改变搜索响应时机、不修改比较器或筛选语义。后续若仍需处理万条规模，再独立评估异步计算与结果版本控制。

必须覆盖：无结果、空数据、升降序、协议/策略组合筛选、选中连接消失、详情实时更新、右键创建分流规则、刷新时滚动位置及页面回收重建。

## 2. 次优先：连接数据未变或仅选择变化，也整表重载

位置：`Sources/LumaRoute/Stores/AppStore.swift:41`、`Sources/LumaRoute/Views/ConnectionTableView.swift:87`。connections 无条件发布，新快照即使内容完全一致也触发上游计算；Coordinator.update 每次无条件 reloadData。

两轮注入 6 次相同的 2,000 条连接，都得到 24 次 items 计算和 6 次整表重载。只改变 selection 时也至少每次一次整表重载。单轮共享结果原型能去掉重复计算，但仍然会重载表格，因此这是独立的后续机会。

建议区分“行内容/顺序改变”和“选中状态改变”：相同数据跳过发布或重载，选择变化只同步选择。先做完整正确的内容比较，再考虑更细的行更新。

不能只按连接 ID 判断相同：下载、上传、进程信息、策略链和详情字段仍可能改变。即使跳过重载，也必须更新 coordinator.parent，保持右键操作、目标策略和 busy 状态有效。不以减少实时字段刷新来换性能。本轮没有量化单独跳过 reloadData 的收益，不能把第 1 项的耗时收益重复计算。

## 3. 按规模处理：菜单预建全部候选，并刷新未显示子菜单

位置：`Sources/LumaRoute/App/StatusMenuController.swift:102`、`:146`、`:282`、`:298`。根菜单首次创建全部策略组的候选项；任意菜单展开期间，每 150 ms 执行完整 stateUpdates。菜单关闭后会停止定时器，不能将这项开销描述为全天后台耗电。

真实菜单方法的两轮测量：

| 组数 × 每组节点数 | 首次构建 | 状态不变时每轮刷新中位数 | 每轮状态回调数 |
| --- | ---: | ---: | ---: |
| 5 × 100 | 23.35–24.88 ms | 0.51–0.64 ms | 516 |
| 10 × 300 | 88.10–90.05 ms | 2.15–2.22 ms | 3,021 |
| 20 × 1,000 | 568.47–570.62 ms | 14.51–15.11 ms | 20,031 |

同一节点可能出现在多个组中，故条目数不等于唯一节点数。小配置开销较小；大订阅或组合订阅首次打开菜单可能出现可感知停顿。定时刷新测的是生产刷新方法本身，不包含 macOS 菜单绘制时间。

建议按展开情况延迟构建子菜单，只刷新可见菜单及必要父项。须保留勾选、延迟测速实时进度、快捷键、悬停高亮、组结构变化时的安全更新和菜单关闭后的停表行为。此项比第 1 项改动范围大，适合单独实现和回归。

## 4. 较低优先级：日志搜索重复扫描缓存

位置：`Sources/LumaRoute/Views/LogsPage.swift:26`。在未选择日志的场景，计数与列表各计算一次 items。2,000 条日志、每批追加一条并移除最早一条，两轮各测 6 次：

| 搜索条件 | 每次更新的筛选调用数 | 每次更新的筛选总耗时 |
| --- | ---: | ---: |
| 无搜索 | 2 | 约 0.01 ms |
| 部分匹配 | 2 | 8.12–8.87 ms |
| 无匹配 | 2 | 12.62–12.84 ms |

只有带筛选并持续追加日志时收益较明显；未筛选时已直接返回日志数组，没有必要额外缓存。建议先在同轮渲染共享结果，保留现有暂停快照、选中详情、自动滚动、清空、导出范围与脱敏规则。搜索增量缓存涉及过期淘汰与暂停/继续，不能当作无风险的小改动。

## 暂不建议优先调整

- 进程补全：本机 300 / 2,000 / 10,000 条合成未补全连接，当前查询中位数约 3.36 / 4.91 / 14.39 ms；按协议和端口建索引的副本约 3.42 / 4.58 / 7.63 ms。正常规模收益有限。10,000 条已有进程路径的连接约 1.77 ms，已走跳过扫描路径。长时间缓存进程归属存在端口/PID 复用及多进程歧义风险，不应为这点收益弱化正确性。
- 字节格式化：2,000 次调用，新建 ByteCountFormatter 约 15.75 ms，复用约 15.91 ms，输出一致但没有测出收益，不建议据“对象创建看起来很多”就修改。
- 日志入口：10,000 条约百字符普通日志创建及脱敏累计约 271.57 ms，是同步批量微测，不代表日常每秒会有该数量日志。正则已静态缓存，日志已有 150 ms 批量发布及 2,000 条上限。不能跳过脱敏来加速。
- 配置解析/组合与磁盘操作已有 actor/异步处理；规则表格固定行高及行视图复用、闲置页面回收、按页面和可见性请求数据均仍存在。本轮未发现需要推翻这些机制的证据。
- 未进行外部测速、大流量转发、真实订阅切换或长期功耗压测，因此不对代理吞吐、首次连接耗时、耗电或内核峰值内存下新结论。
