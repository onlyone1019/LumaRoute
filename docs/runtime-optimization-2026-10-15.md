# Build 22：订阅去重、运行恢复与存储优化

## 行为

- 机场订阅按 UTF-8 原文比较。内容相同只刷新用量和更新时间，不重新调用 Mihomo 校验、应用配置或重启状态流。规则订阅也复用原 revision。存储层再次去重，重复保存不会覆盖上一份有变化的配置。
- 流量、日志在异常和正常 EOF 后自动重连，等待间隔依次为 1、2、4、8、16 秒，长连接正常运行超过 10 秒后重新从短间隔开始。配置替换、睡眠和退出会取消旧任务，旧任务不能发布新状态。
- 节点、连接、规则列表读取失败保留上次数据。版本接口连续三次健康检查失败才进入内核恢复；确认本地进程退出或后台服务报告退出则立即恢复。版本接口和心跳用服务请求各最多等待 3 秒，单次服务通信失败不会单独停止正常内核。三次检查的实际时间包含请求耗时和轮询间隔，并非固定六秒。
- 自动更新使用独立任务，下载串行进行，下载阶段不占全局 busy，也不阻塞健康轮询。完成下载后等待前台操作结束，再串行校验、应用和提交。提交前重新读取最新应用状态；排队项目开始前重新检查到期状态和自动更新开关；同一订阅合并重复更新，已删除或修改的订阅不接受旧下载结果。取消会传递到 curl 和配置校验进程，退出等待后台任务收尾。
- 应用层 SQLite 保存、提交、备份、缓存清理移到串行存储队列。普通设置只写 app_state，节点选择只写对应 choice；复合业务提交仍使用原子事务，按记录增量更新和删除，拒绝重复标识。没有更换数据库路径、格式版本或日志模式。
- 准备配置时最多每五分钟清理一次 runtime/revisions。保留当前内存配置和 active.yaml 引用的目录、最近 20 份及一小时内的所有目录；引用解析失败、未知目录和符号链接均不删除。新建自动备份保留最近十份，并保护正在恢复的源备份；手动备份和此前没有自动标识的备份不清理。
